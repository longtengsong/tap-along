# 最小开发任务 · 编辑/补一句后的引导刷新

**任务编号：** MINI-GUIDE-REFRESH-001

**状态：** 已实现（G1–G5 代码完成，待真机验收）

**估时：** 1.5–2 人日（单人，含单测与回归）

**新增依赖：** 无

---

## 1. 一句话目标

用户编辑批注或补一句后，在现有“维护老师回应”结束之后，自动用最新正文重新找一次接点：

- 找到新的相关旧页 → 显示新的引导卡片；
- 没有接点 → **不显示**“这轮不追问”，因为维护老师已经问过一个问题了；
- 刷新期间用户继续落笔或合上页面 → 丢弃这次刷新，不出现迟到卡片。

这是对已完成的“新页边引导”的生命周期补全，不改新建笔记链路、不改联网问答、不改 prompt。

---

## 2. 本任务做什么、不做什么

### 2.1 做

- 编辑/补一句成功后，记一个页面级标记：这页需要刷新引导。
- 等现有维护老师回应完成（`teacher:done` 且 `kind === 'maintenance'`）后，自动触发一次引导刷新。
- 刷新使用最新正文、FTS 候选和现有 GuidancePlanner。
- 刷新只处理 `needed`：
  - `needed`：写入并显示新卡片；
  - `not_needed` / `no_candidates` / `failed`：静默结束，不显示提示、不改开场问题。
- 刷新时页面已经可能有用户消息，允许继续；但如果在刷新期间出现**新的用户消息**，丢弃结果。
- 刷新不写开场问题，不删除维护老师消息，不增加教学轮次。
- 同一页面同一时间只允许一个刷新任务；引导 IPC 的幂等和取消沿用现有结构。
- 新增 `guidance:run` 窄接口，便于测试和后续手动刷新。

### 2.2 不做

- 不做每次用户回复后的自动重跑。
- 不做手动“再找找”按钮。
- 不做刷新失败提示；静默失败，用户仍可继续写。
- 不做新的卡片 UI；复用现有 `GuidancePanel`。
- 不改 `findRelatedNotes` / FTS / 短词召回。
- 不改联网问答、设置、来源列表。
- 不做编辑后立即刷新与维护老师回应并行；必须等维护回应结束，避免两个问题同时出现。
- 不把刷新结果写入开场问题，也不移除维护消息。

## 3. 当前行为与目标行为

### 3.1 当前行为

```text
改批注 / 补一句
  → editText / appendText
  → clearGuidanceAfterBodyChange
       ├─ 清空 guidance
       └─ 移除隐藏的 opening
  → 写入 maintenance 胶囊
  → respondAfterMaintenance
       → 老师针对这次修改问一个问题
  → 结束
```

结果：编辑后只保留维护老师的问题，不再有“相关旧页”接点。

### 3.2 目标行为

```text
改批注 / 补一句
  → 清空旧 guidance
  → 标记 pendingGuidanceRefresh = true
  → 维护老师回应（保持不变）
  → teacher:done(kind = maintenance) 成功
  → guidance:run(mode = refresh)
       ├─ needed → 新卡片出现
       └─ 其他 → 静默
  → 用户可点击卡片，走现有 guidance:use
```

关键顺序：

1. 维护老师回应先结束；
2. 再刷新引导；
3. 用户如果在这之间继续写，刷新结果作废。

## 4. 最小技术方案

### 4.1 数据与状态

不新增数据库列。

渲染层 `PageRecord` 增加一个**内存态**字段：

```ts
pendingGuidanceRefresh?: boolean;
```

- 编辑/补一句成功后置 `true`；
- 维护回应成功结束后读取并清零；
- 不改数据库，重启后自然消失，不需要迁移。

### 4.2 引导服务刷新模式

`GuidanceService.run(pageId, emit, options?)` 增加：

```ts
interface GuidanceRunOptions {
  mode?: 'initial' | 'refresh';
}
```

- `initial`：现有行为，完全不变。
- `refresh`：
  - 允许页面已有用户消息；
  - 不要求页面没有 guidance（但编辑时已经清空）；
  - 捕获 `expectedMessageCount = page.messages.length`；
  - 只处理 `needed`；
  - `finalizeGuidance` 使用：
    - `removeOpening: false`
    - `allowUserMessages: true`
    - `expectedMessageCount`
  - 如果 `not_needed` / `no_candidates` / `failed`：直接返回，不写库、不发事件。
  - 如果页面在规划期间新增消息（用户落笔、老师维护消息追加等），`finalizeGuidance` 因消息数不一致返回 `null`，结果丢弃。
  - 如果页面关闭，丢弃。

### 4.3 仓储 `finalizeGuidance` 扩展

现有选项：

```ts
{
  removeOpening: boolean;
  expectedBody: string;
}
```

增加可选字段：

```ts
{
  allowUserMessages?: boolean;       // 默认 false，保持 initial 行为
  expectedMessageCount?: number;     // 设置后必须与当前消息数一致
}
```

校验顺序：

1. 页面存在、仍 `reading`；
2. 正文等于 `expectedBody`；
3. 如果 `allowUserMessages !== true`，页面不能有用户消息；
4. 如果设置了 `expectedMessageCount`，当前消息数必须相等；
5. 可选移除 `opening`；
6. 写 guidance。

这样初刷新的行为不变，刷新模式不会误删开场问题，也不会把过期卡片贴到用户已经继续聊的页面上。

### 4.4 IPC 与 preload

新增：

```ts
GUIDANCE_CHANNELS.run = 'guidance:run';

interface GuidanceRunPayload {
  pageId: number;
  mode: 'refresh';
}

interface GuidanceRunResult {
  ok: boolean;
  errorCode?: AppErrorCode;
}
```

- `guidance:run` invoke：
  - 校验 pageId / mode；
  - 调用 `GuidanceService.refresh(payload, emit)`；
  - 立即返回 `{ ok: true }`，实际任务异步跑；
  - `emit` 通过 `event.sender` 发送 `guidance:updated`，窗口关闭时丢弃。
- preload / `TapAlongBridge` 增加 `runGuidance`。
- `guidance:updated` 事件沿用现有结构，不需要新字段。

### 4.5 渲染层接入

- `saveEditing` / `submitAppend` 成功、`clearGuidanceAfterBodyChange` 后：
  - `page.pendingGuidanceRefresh = true`。
- `handleTeacherDone`：
  - 维护请求成功结束后，读取 `pendingGuidanceRefresh`；
  - 清零；
  - 页面仍存在且 `reading` 时调用 `refreshGuidance(page)`。
- `handleTeacherDone` 的失败、取消分支：清零标记，不刷新。
- `refreshGuidance(page)`：
  - `tapAlongApi.supportsGuidanceRefresh()`；
  - 调 `runGuidance({ pageId, mode: 'refresh' })`；
  - 不设置本地 pending 面板，不显示 loading；
  - 结果通过 `guidance:updated` 到达，卡片自然出现；
  - 失败静默，不弹蒙层。
- 用户发送新消息时：
  - 如果刷新还在跑，服务端会因消息数变化丢弃；
  - 本地不需要额外处理；
  - 如果卡片已经出现，按现有逻辑隐藏（有用户消息时 `GuidancePanel` 不显示）。

### 4.6 顺序与幂等

```text
edit / append
  → clear guidance
  → pendingGuidanceRefresh = true
  → maintenance teacher request
  → teacher:done(maintenance, ok)
  → pendingGuidanceRefresh = false
  → guidance:run(refresh)
```

- 维护回应失败/取消：不刷新。
- 同一页面连续编辑两次：
  - 第一次维护回应结束后刷新；
  - 第二次编辑会重新清空 guidance 并再置标记；
  - 第二次维护回应结束后再刷新。
- 同一 `pageId` 已有 in-flight 引导任务时：
  - 如果是同一模式的重复请求，复用现有任务；
  - 如果已有的是 initial、这次是 refresh，刷新必须**排在 initial 之后**执行，不能直接复用旧任务把刷新吞掉；
  - 如果是 refresh 正在进行，新的 refresh 直接复用；避免并发写两次。
- 刷新结果 `needed` 才写；其他状态不写。

## 6. 验收清单

### 6.1 功能

1. 编辑一条已有旧页关联的笔记：
   - 维护老师先问关于修改的问题；
   - 维护回应结束后，出现新的接点卡片；
   - 点击卡片仍走现有 `guidance:use`。
2. 编辑成一条没有接点的笔记：
   - 维护老师正常回应；
   - 不出现“这轮不追问”；
   - 不出现空卡片面板。
3. 编辑后维护老师回应失败：
   - 不触发刷新；
   - 不出现迟到卡片。
4. 刷新期间用户继续落笔：
   - 刷新结果被丢弃；
   - 不出现遮挡用户消息的卡片。
5. 刷新期间用户合上这页：
   - 不写 guidance；
   - 不发事件。
6. 连续编辑两次：
   - 每次维护回应结束后各自刷新；
   - 不并发写入两次 guidance。
7. 新建笔记首次引导：
   - 行为与现在完全一致；
   - 仍能出卡片 / 不追问 / 回退开场问题。

### 6.2 兼容

- `guidance:use`、`guidance:updated` 结构不变。
- FTS / 短词召回 / 联网问答 / 设置不改。
- 旧数据库不需要迁移。
- 浏览器 mock 不触发 refresh（无 bridge 时 no-op）。

### 6.3 质量

- `npm test` 全绿；主进程覆盖率 ≥ 90%。
- `tsc --noEmit`、`oxlint`、`oxfmt --check` 通过。
- 无新增运行时依赖。

## 8. 风险与边界

| 风险                   | 影响                 | 处理                                             |
| ---------------------- | -------------------- | ------------------------------------------------ |
| 维护问题与卡片同时出现 | 用户被两个方向拉扯   | 严格等维护 `teacher:done` 后再刷新；不并行       |
| 刷新结果迟到           | 用户已经开始新对话   | 捕获 `expectedMessageCount`，消息数变化即丢弃    |
| 维护失败仍刷新         | 出现无来由卡片       | 只在维护成功后触发；失败/取消清零标记            |
| 编辑时 initial 仍在跑  | refresh 被旧任务吞掉 | refresh 排队到 initial 之后；不复用 initial 结果 |
| 重复编辑并发刷新       | 重复写 guidance      | 同模式复用；不同模式排队；同一页串行             |
| 刷新静默失败           | 用户不知道           | 刻意如此；维护问题仍在，不打断                   |
| 额外模型调用           | 编辑成本增加         | 仅在编辑/补一句后触发；可后续加开关              |
| 旧数据无 pending 标记  | 不影响               | 内存态，不持久化；重启后不自动刷新               |
| 刷新写入覆盖已有卡片   | 旧卡片丢失           | 编辑时已清空 guidance；刷新只处理 needed         |

## 10. 待确认

1. **刷新是否只处理 `needed`？**
   - 建议：是。维护老师已经问过问题，再显示“这轮不追问”会自相矛盾。

2. **维护失败时是否也刷新？**
   - 建议：不刷新。用户没有收到维护问题，再突然出现卡片会显得无来由。

3. **刷新期间用户落笔，是否丢弃？**
   - 建议：丢弃。用消息数做一致性校验，避免过期卡片贴到新对话上。
