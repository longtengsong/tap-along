# 反馈处理手册 · TapAlong

> 目的：在 alpha 阶段，用最少的人力把反馈变成可行动的信息，同时不破坏「只提问、不代写、本地优先」的定位。
> 前提：**没有遥测、没有埋点、没有账号体系**。所有反馈都来自用户主动说出来；不要假装它代表全部用户。

## 0. 六条原则

1. **先听场景，再谈功能。** “你当时在做什么”比“你要什么功能”更有信息量。
2. **区分需求与方案。** 用户说“加个一键总结”，需求可能是“我回看时抓不住重点”；方案不一定要接受。
3. **定位不是投票。** 与「只提问、不代写」「数据留在本机」冲突的请求，礼貌拒绝，不因为声音大就改。
4. **不辩论，不讨好。** 一次事实澄清足够；不承诺时间表，不写“马上”。
5. **保护隐私。** 不主动索要笔记正文、API Key、截图中的个人信息；引用要征得同意并匿名。
6. **闭环。** 用户花时间反馈，至少要知道“收到了 / 不做什么 / 改了什么”。

## 1. 反馈入口

| 入口                         | 适合                              | 响应目标                 | 备注                               |
| ---------------------------- | --------------------------------- | ------------------------ | ---------------------------------- |
| GitHub Issues                | 可复现 bug、具体需求              | 工作日 48 小时内首次回应 | 用模板；不要让用户填隐私           |
| GitHub Discussions           | 安装/配置问题、开放想法、用法分享 | 工作日 48 小时内         | Q&A / Ideas / How I use it         |
| 安全问题                     | 漏洞、密钥泄露、注入              | 尽快，私下处理           | 不用公开 issue；按 SECURITY.md     |
| 15 分钟访谈                  | 愿意深聊的用户                    | 约在 3 个工作日内        | 自愿；可匿名                       |
| 渠道评论（V2EX/HN/小红书等） | 首轮传播反馈                      | 当天尽量回               | 不把评论当工单；引导到 GitHub      |
| 应用内反馈                   | **目前没有**（已核实）            | —                        | alpha 可接受；若要加，另开代码任务 |

**不以私人邮箱、微信群、电话作为正式支持入口。** 正式反馈集中到 GitHub，方便后来的人搜索。

## 2. 标签体系

### 2.1 kind/\*：每条 issue 恰好一个

| 标签                 | 定义                                | 退出条件                                          |
| -------------------- | ----------------------------------- | ------------------------------------------------- |
| `kind/bug`           | 行为与文档/预期不符，且可复现       | 修复并验证，或转为 `alpha-limitation` / `wontfix` |
| `kind/feature`       | 请求新能力；必须带场景              | 转 `adopted` / `deferred` / `wontfix`             |
| `kind/question`      | 安装、配置、用法问题                | 回答后转 Discussion 或关闭                        |
| `kind/docs`          | README、PRIVACY、安装步骤错误或缺失 | 文档合并                                          |
| `kind/design`        | 交互、文案、视觉问题，不是功能故障  | 设计决定或合并                                    |
| `kind/compatibility` | macOS 版本、芯片、模型/供应商兼容性 | 确认支持范围或记为限制                            |

> 现有 Issue 模板会自动打 `bug` / `enhancement`。**保留这两个标签**，triage 时再加 `kind/*`；不要重命名模板里的标签，否则新 issue 会丢标签。

### 2.2 area/\*：1–2 个

`area/onboarding` · `area/companion` · `area/guidance` · `area/conversation` · `area/research` · `area/editor` · `area/images` · `area/retrieval` · `area/settings` · `area/data` · `area/i18n` · `area/packaging` · `area/a11y`

### 2.3 流程标签

| 标签                 | 含义                                 | 使用规则                                                                         |
| -------------------- | ------------------------------------ | -------------------------------------------------------------------------------- |
| `needs-info`         | 缺版本、macOS、安装方式、复现步骤    | 一次性问清所有缺失项；7 天后无回复则关闭，注明“可随时重开”                       |
| `needs-repro`        | 有步骤但维护者复现不了               | 请用户补日志/录屏/commit；7 天后无回复则关闭                                     |
| `good-first-issue`   | 范围清楚、有测试路径、不需要产品决策 | 附文件路径、验收标准、测试命令；**不要**用于安全、数据丢失、打包签名、提示词注入 |
| `adopted`            | 方向一致，维护者会排期               | **不是交付承诺**；60 天未动要重评或改 `deferred`                                 |
| `alpha-limitation`   | 已知限制，已在 README/Release 说明   | 关闭时给链接，不要标 `wontfix`                                                   |
| `deferred`           | 方向可能一致，但 alpha 阶段不做      | 写“为什么现在不做”，不写日期                                                     |
| `blocked`            | 依赖外部（证书、供应商、上游）       | 写清依赖项和解除条件                                                             |
| `duplicate`          | 与已有条目重复                       | 链接 canonical issue 后关闭                                                      |
| `wontfix`            | 与定位冲突或明确不做                 | 必须写理由 + 替代方案；用 §6 模板                                                |
| `feedback-interview` | 用户愿意接受 15 分钟访谈             | 记录同意范围；不公开个人信息                                                     |

### 2.4 状态流转

```text
新 issue
  ├─ 安全/密钥 → 私下 advisory（不在公开区讨论细节）
  ├─ 问题 → 回答 → Discussion / 关闭
  ├─ bug → 可复现？ → adopted / good-first-issue
  │           └─ 不可复现 → needs-repro → 7 天关闭
  ├─ feature → 定位一致？ → adopted / deferred
  │                └─ 冲突 → wontfix + 模板
  └─ 已知限制 → alpha-limitation + 文档链接
```

**规则**：没有 `kind/*` 或 `area/*` 的 issue 不得留在 inbox 超过 7 天；`wontfix` 必须有理由；`adopted` 不是“已答应”。

## 3. 每周 triage 例程

固定一个 60 分钟时段（建议周一或周五），关掉聊天，只做 triage。

| 时间      | 动作                                                                | 产出                                  |
| --------- | ------------------------------------------------------------------- | ------------------------------------- |
| 0–5 min   | 扫 Issues / Discussions / 安全通知；有密钥或隐私内容立即处理        | 安全项清零或转私下                    |
| 5–15 min  | 每条新条目：打 `kind/*` + `area/*`；缺信息加 `needs-info`；先回一句 | 无未分类新条目                        |
| 15–30 min | 复现 1–2 个高优先 bug；验证已修复项；更新 `adopted` 进度            | 每个 bug 有“可复现/不可复现/已修”结论 |
| 30–40 min | 把本周反馈归成 3–5 个主题；更新反馈日志；挑 1 个 `good-first-issue` | 主题清单 + 1 个可贡献项               |
| 40–50 min | 补 FAQ / 置顶帖 / 文档；回 Discussions 的开放问题                   | 至少 1 处文档更新或明确“不需要”       |
| 50–60 min | 写 5 行周记：新增、关闭、卡点、下周、停止做什么                     | 周记发到 `Alpha notes`（可只写事实）  |

**30 分钟精简版**（忙周）：0–5 安全；5–15 分类 + 首次回应；15–25 复现/归主题；25–30 写周记。宁可少做，不要漏安全。

**每条 issue 的完成定义（DoD）**：有 kind、有 area、有下一步（修复/等 info/转讨论/关闭理由），或已关闭。仅打标签不算完成。

### 3.1 首次回应模板

**Bug（可复现）**

```text
谢谢，按你给的步骤我在 <commit> 上复现了。
现在记为 bug；修好后会在 issue 里更新。
目前没有安装包，修复只能从源码拉取；如果你愿意，可以在修好后帮忙验证。
```

**Bug（缺信息）**

```text
谢谢报告。我现在还不能复现，需要三样东西：
1. macOS 版本 + Apple 芯片型号；
2. 安装方式（源码 commit / 哪个 Release）；
3. 最小复现步骤 + 应用内错误提示（请去掉 API Key 和笔记正文）。
有这些我再试一次。
```

**Feature**

```text
谢谢，这个场景很清楚：你在 <场景> 里想 <结果>，现在只能 <workaround>。
我想确认一下：如果只能解决一半，你最希望先解决哪一半？
这不一定进 alpha，但会作为方向记录。
```

**重复**

```text
这个和 #<编号> 是同一个问题，我在那边继续跟进，先把这个关掉。
如果你有新的复现信息，欢迎补到原 issue。
```

**已修复**

```text
已在默认分支（main/master）修复（<commit>）。目前没有签名安装包，需要从源码更新后验证。
如果仍然出现，请在这个 issue 里补新的复现步骤。
```

## 4. 15 分钟用户访谈

### 4.1 招募

- 从明确写出“我会拿它做 X”或“我卡在 Y”的人里邀请，不群发。
- 说明：15 分钟、不推销、可以跳过任何问题、不录音也可以、引用会匿名。
- 不要求对方准备笔记；不要让对方展示私人内容。

### 4.2 开场（1 分钟）

```text
谢谢你把时间。我想了解你真实的用法，不是让你评价好坏。
我会记几笔，只用于改产品；引用你的话会匿名，发之前可以再确认。
不想回答的可以直接跳过；现在开始录音可以吗？
```

English:

```text
Thanks for the time. I want to understand how you actually use it, not whether you like it.
I'll take a few notes for product work only. If I quote you, it will be anonymized, and you can review it first.
Skip anything you don't want to answer. Is it okay if I record?
```

### 4.3 五个问题（约 12 分钟）

1. **最近一次**：你最近一次读到一段想记下来的东西，是什么场景？当时你做了什么？
2. **回看**：你上一次回看旧笔记是什么时候？当时想找什么？找到了吗？
3. **卡点**：刚才试用时，哪一步让你停顿或犹豫？你当时以为会发生什么？
4. **问题质量**：伴读的哪个问题让你真的想了一下？哪个问题让你觉得被审问，或者像在替你下结论？
5. **失去它**：如果明天这个应用消失，你会缺什么？你会拿它做什么？

**追问**（不要引导）：

- “能举一个具体例子吗？”
- “当时你实际做了什么？”
- “为什么那样做？”
- “如果只能保留一个功能，你留哪个？为什么？”

**不要做**：中途演示、纠正用户、解释设计、辩护、问“你觉得好不好”、问“你会不会付费”、问“你认识谁会需要”。

### 4.4 记录模板（存在私有位置）

```text
日期：
渠道 / 匿名代号：
同意引用：是 / 否
同意录音：是 / 否 / 未录
最近一次使用场景：
回看旧笔记的习惯：
卡住的步骤：
有效的问题 / 让人不适的问题：
如果消失会缺什么：
原话（匿名，最多 2 句）：
后续动作（修 bug / 改文案 / 只记录）：
```

### 4.5 结束（2 分钟）

```text
今天最有用的两点是 <A> 和 <B>。
我会把 <A> 带进下月的优先级讨论；<B> 我现在不能承诺，但会带回去讨论。
如果后面需要确认引用，我会再发你一次；你也可以随时让我删掉记录。
```

两周内回一次“我们改了什么/没改什么”。不承诺具体版本时间。

## 6. 与定位冲突的请求：礼貌拒绝模板

先说结构：**复述需求 → 说明约束 → 明确不做 → 给替代 → 不承诺**。不要用“我们会考虑的”敷衍；也不要说“这个需求不重要”。

### 6.1 代写、总结、续写、生成整篇

**中文**

> 谢谢你把这个场景讲清楚。你要的是让伴读直接产出成稿/摘要，省掉自己组织的过程。这个请求和现在的定位冲突：它只提问，不替你写；做了它就不是同一个工具。所以不会做。现在能帮的是把相关的旧念头找出来、问一个问题，让你自己写；如果你需要成稿，通用写作工具可能更合适。

**English**

> Thanks for spelling out the situation. What you're asking for is for the companion to produce the draft or summary for you. That conflicts with the premise: it asks; it doesn't write for you. Building it would make this a different tool, so we won't. What TapAlong can do today is surface the earlier thoughts and ask one question so you can write it yourself. If you need a finished draft, a general writing tool may fit better.

### 6.2 云同步、账号、团队协作

**中文**

> 云同步、账号和团队协作都需要服务端，也会改变“数据留在本机”这个前提，所以当前不做。现在可以在「设置 → 数据与隐私」导出 `backup.json + images/`，把文件夹放到你自己选择的位置；但还没有导入/恢复，alpha 阶段请保留原始数据。

**English**

> Cloud sync needs accounts and a server, and it would change the local-first premise, so we're not doing it now. Today you can export `backup.json + images/` from Settings → Data & privacy and put the folder wherever you like. There's no import/restore yet, so keep your original data during the alpha.

### 6.3 埋点、使用统计、增长推送

**中文**

> 我们不加埋点，也不做使用统计。想了解你怎么用，我们更愿意做 15 分钟访谈，只记录你同意的内容。推送/streak 这类增长机制也不在方向里。

### 6.4 自动判断“哪些念头重要”、自动下结论

**中文**

> 如果它替你判断哪些念头重要、替你下结论，就变成了代答。这个不做。它可以问一个让你自己判断的问题，但选择仍然留给你。

### 6.5 平台请求（Windows / Linux / 移动端）

这不是定位冲突，是范围问题，用“暂缓”而不是“拒绝”：

> 当前只支持 macOS 13+ / Apple 芯片；Windows、Linux 只在路线图里评估，没有时间表；移动端没有计划。先把 macOS 的 alpha 做稳；如果你愿意，可以在 Discussions 里写你的使用场景，帮我们判断优先级。

### 6.6 导出到 Notion / Obsidian 等

> 这不是定位冲突，但不在 alpha 范围。现在有 JSON 导出（`backup.json + images/`），没有导入/恢复；你可以先自己转换。想要哪种格式，欢迎在 Ideas 里写具体场景，不要只写“支持 Notion”。

### 6.7 回复长度

- 公开评论：2–4 句，给一个链接，不写长文。
- Issue：可以长一点，但必须包含“不做什么”和“现在能做什么”。
- 不反复解释同一个拒绝；第二次直接链接上次回复。

## 7. 反馈日志与隐私

**每条反馈记一行**（私有表格，不进仓库）：

| 字段        | 说明                                                            |
| ----------- | --------------------------------------------------------------- |
| date        | 日期                                                            |
| channel     | v2ex / hn / reddit / jike / matrix / bilibili / xhs / interview |
| consent     | 是否同意匿名引用；是否同意后续联系                              |
| situation   | 用户当时在做什么（用自己的话，不抄笔记）                        |
| quote       | 最多两句原话，匿名                                              |
| theme       | 3–5 个固定主题之一                                              |
| kind / area | 与 issue 标签一致                                               |
| severity    | S1 数据/安全；S2 核心闭环阻断；S3 烦人；S4 打磨                 |
| status      | new / replied / adopted / fixed / declined / deferred           |
| link        | issue/discussion 链接                                           |
| next        | 下一步与日期                                                    |

**隐私规则**

- 不把用户笔记、截图、API Key、邮箱写进日志或仓库。
- 如果用户贴了 Key，先请对方立即撤销/轮换，再编辑掉公开内容；不要复述 Key。
- 引用前问一句“我可以匿名引用你这句吗？”；对方说不行就不引用。
- 访谈记录只存在私有位置；对方要求删除时，24 小时内删掉并确认。
- 公开月报不写可识别信息；小渠道 + 具体身份可能被认出时，再模糊一层。

## 8. 每月质量校准（20 分钟）

- 随机重读 10 个已关闭 issue：标签对吗？关早了吗？`wontfix` 有替代方案吗？
- 检查 60 天以上的 `adopted`：还在做吗？不做就改 `deferred` 并说明。
- 检查 `good-first-issue`：是否真的不需要产品决策？验收标准是否可执行？
- 检查 `needs-info` 关闭记录：有没有因为问得太多把人吓走？
- 检查自己的回复：有没有“其实你不懂”“我们早就考虑过”这类防御性措辞？
- 检查口径：有没有把 `adopted` 说成“已发布”，把“评估”说成“计划支持”？

## 9. 常见错误

- 把 star 数当需求强度。
- 把“用户提了方案”当成“用户需要这个方案”。
- 用 `wontfix` 关掉一个其实只是文档没写清的问题。
- 向用户索要完整笔记或带 Key 的截图。
- 为了“了解用户”加埋点——这和项目承诺冲突。
- 在公开场合承诺“下个版本就做”。
- 引用用户原话不匿名、不确认。
- 被一个声音大的用户带着改定位。
- 只回复活跃用户，忽略“装不上就走了”的沉默大多数。
