## 1. 结论先行

```text
┌────────────────────────────────────────────────────────────┐
│ NoteEditor（TipTap / ProseMirror）                          │
│                                                            │
│  读到一句话，[图片] 后面继续写……                            │
│  图片是行内节点，插在任意光标位置；按容器宽度等比缩放        │
└────────────────────────────────────────────────────────────┘
          │ getJSON()
          ▼
┌──────────────────────┐        ┌──────────────────────────────┐
│ pages.body_doc       │        │ page_images (metadata)        │
│ TipTap JSON          │───────▶│ page_image_refs (page ↔ image)│
│ 文字 + imageId        │        │ userData/images/<id>.webp     │
└──────────────────────┘        └──────────────────────────────┘
          │ derivePlainText()              │
          ▼                                │ read file -> base64
┌──────────────────────┐                    ▼
│ pages.body           │        ┌──────────────────────────────┐
│ 纯文本投影            │        │ 多模态模型请求                │
│ 标题/FTS/检索/摘要    │        │ text + image_url(webp)        │
└──────────────────────┘        └──────────────────────────────┘
```

核心决策：

1. **正文用 TipTap 3 + ProseMirror 编辑**。图片是行内 atom 节点，插在光标处；编辑时直接看到图文混排。
2. **`body_doc` 是排版的唯一事实来源**；`body` 是从文档派生的纯文本投影，继续供标题、FTS、检索、两行摘要使用。
3. **图片存文件，不存 BLOB**。上传前压成 WebP，存 `userData/images/<id>.webp` + `page_images` 元数据 + `page_image_refs` 引用。这样可流式读取、导出直接复制。
4. **`tap-image://img/<id>` 自定义协议** 提供稳定的 `<img src>`；编辑器、大图预览共用。
5. **不做数量/大小上限，但上传前统一压缩**：最长边 2400px、WebP 质量 0.9，动图保留首帧；压缩后仍不设固定 MB 上限。
6. **读态卡片保持两行文本摘要**，不展示图片；卡片头部有「含图 N 张」和「查看全文」；全文浮层只读展示完整图文，图片按容器等比缩放。编辑态同样展示完整图文并内部滚动。
7. **图片按容器宽度等比缩放**：`max-width: 100%; height: auto`，不裁剪、不拉伸；窗口变化时自然回流。
8. **正文必须至少有一句文字**，纯图片念头不允许保存。
9. **图片作为多模态上下文发送给当前模型**：当前念头的图片随老师对谈、理解引导、联网问答、意图路由一起发送；恢复上下文时发送目标页和上下文页的图片。发送前做图片能力检测：供应商不支持就自动降级为纯文本请求，避免流程中断。
10. **导出改目录**：`backup.json` + `images/`；不把图片 base64 塞进单个 JSON。
11. **旧数据只增不改**：旧念头没有 `body_doc`，继续按纯文本显示；第一次编辑时生成文档；旧草稿自动转换。

## 2. 需求与边界

### 2.1 做

- 新念头正文支持在任意光标位置粘贴图片，并立即在编辑器里显示。
- 编辑已有念头同样支持；图片可插在文字中间、段首、段尾、独立成段。
- 一次粘贴多张；不限制张数、不限制单张原始字节；上传前统一压缩为 WebP。
- 支持删除、撤销/重做、应用内复制图片到另一条念头。
- 编辑态完整图文展示，编辑器内部滚动；图片按容器等比缩放。
- 读态卡片保持两行摘要，头部显示含图数量；点「查看全文」打开只读图文浮层。
- 草稿恢复包含文字和图片位置。
- 编辑取消/保存失败不破坏原内容。
- 导出备份包含图片文件。
- 清理未引用图片、磁盘孤儿文件和临时文件。
- 图片作为多模态内容发送给当前模型；发送前检测供应商是否支持图片，不支持则只发文字。
- 旧念头、旧草稿继续可用。

### 2.2 不做

- 不做图片 OCR、裁剪、旋转、标注、滤镜、压缩设置。
- 不做图片拖拽改大小、对齐方式、图文环绕。
- 不新增文字格式（粗体、斜体、标题、列表、链接）；保留纯文本换行/空行。
- 不做纯图片念头。
- 读态卡片本身不展示图片；完整图文通过「查看全文」只读浮层展示。
- 不做拖拽文件进窗口（只做剪贴板粘贴）。
- 不做从 Finder / 资源管理器复制文件路径的粘贴。
- 不做「补一句」输入框和对谈输入框的图片。
- 不做归档列表缩略图。
- 全文浮层暂不支持复制/下载图片。
- 不做基于模型名称的静态能力表；用真实探测请求判断供应商是否支持图片。

### 2.3 明确取舍

- **正文必须非空**：图片不能单独成篇；保存时 `derivePlainText(doc).trim()` 为空就报 `INVALID_BODY`。
- **图片会在能力检测 supported 时离开本机**：图片作为多模态上下文发送给当前配置的模型供应商；探测本身只发内置极小图。
- **做能力检测**：首次带图请求前（或按缓存）用一张很小的 WebP 探测供应商；不支持就自动去掉图片，纯文本请求继续。
- **格式白名单**：输入 PNG / JPEG / WebP / BMP / AVIF；拒绝 SVG、TIFF、HEIC、GIF。入库统一为 WebP。
- **超大图**：不设固定 MB 上限；压缩后仍受 renderer 内存、IPC 峰值、磁盘、模型请求体积/超时约束。
- **读态摘要 + 全文浮层**：卡片仍两行摘要；点「查看全文」打开只读图文浮层，不再需要进编辑。

## 3. 关键技术选型

### 3.1 编辑器：TipTap 3 / ProseMirror

| 方案                       | 结论                                                                                           |
| -------------------------- | ---------------------------------------------------------------------------------------------- |
| **TipTap 3 + ProseMirror** | **采用**。成熟 contenteditable 封装；中文 IME、撤销/重做、选区、粘贴、节点 schema、JSON 序列化 |
| 自研 contenteditable       | 不采用。Enter/Backspace/粘贴/IME/撤销/HTML 规范化全要自己处理，回归面过大                      |
| 文本块 + 图片块编辑器      | 不采用。中途插入会把一句拆成两个输入框，跨块光标/删除合并/撤销都别扭                           |
| Markdown 源码 + 预览       | 不采用。编辑时看不到图片，不满足「展示出来」                                                   |

依赖（安装时锁定版本，确认 Vue 3.5 / Vite 8 兼容）：

```text
@tiptap/vue-3
@tiptap/core
@tiptap/pm
@tiptap/extension-document
@tiptap/extension-paragraph
@tiptap/extension-text
@tiptap/extension-hard-break
@tiptap/extension-placeholder
@tiptap/extension-history（TipTap 3 若改名为 undo-redo，以实际包名为准）
```

- 只启用最小 schema：`doc → paragraph → text / hardBreak / noteImage`；不启用加粗、斜体、链接、列表、标题、代码块。
- 图片用自定义 `noteImage` 原子节点，不用自带 Image 扩展；需要 `imageId`、上传中状态、删除/预览按钮。
- 包体预计增加 150–250KB（gzip），Electron 可接受。

### 3.2 图片存储：文件 + 元数据 + 引用

| 方案                          | 结论                                                            |
| ----------------------------- | --------------------------------------------------------------- |
| SQLite BLOB                   | 不采用。不限大小时库膨胀、WAL 压力、导出要 base64、读取要过 IPC |
| **文件 + DB 元数据 + 引用表** | **采用**。适合大文件、可流式、导出直接复制、库保持小            |

- 目录：`app.getPath('userData')/images/`。
- 文件名：`<uuid>.<ext>`；内容不可变，可长缓存。
- 数据库只存 `file_name / mime / byte_length / created_at` 和引用关系。
- 写入：先写临时文件，再 `rename`；成功后才写 DB；DB 失败则删文件。

### 3.3 图片读取：自定义协议

| 方案                       | 结论                                                                 |
| -------------------------- | -------------------------------------------------------------------- |
| Data URL                   | 不采用。文档/IPC 变重                                                |
| Blob URL                   | 不采用。富文本回填要异步替换 DOM，打断撤销/选区，还要引用计数        |
| **`tap-image://img/<id>`** | **采用**。一次注册，`<img src>` 直接用；主进程按 id 查库、流式读文件 |

- `app.ready` 之前 `protocol.registerSchemesAsPrivileged`，之后 `protocol.handle`。
- 只接受 `img/<uuid>`；查不到返回 404；不接受任意路径。
- 响应头：`Content-Type`、`Content-Length`、`Cache-Control: private, max-age=31536000, immutable`、`X-Content-Type-Options: nosniff`。

### 3.4 模型请求：OpenAI 兼容多模态 + 能力检测

- 应用面向 OpenAI 兼容的 Chat Completions 供应商；多模态按同一格式扩展：
  ```json
  {
    "role": "user",
    "content": [
      { "type": "text", "text": "..." },
      {
        "type": "image_url",
        "image_url": { "url": "data:image/webp;base64,..." }
      }
    ]
  }
  ```
- 图片以 data URL 发送；入库统一 WebP，因此数据 URL 固定 `image/webp`。
- **发送前做能力检测**：用一张很小的 WebP 发一次 `max_tokens: 1` 的探测请求。
  - 2xx → 支持，后续带图；
  - 400 / 415 / 422 → 不支持，自动去掉图片，纯文本请求继续；
  - 401 / 403 / 404 → 不支持（配置/模型本身有问题，主请求仍会报自己的错）；
  - 429 / 网络错误 / 超时 → 未知，本次纯文本，短时间后重试探测，不阻断主流程。
- 能力结果按「供应商 + model + baseUrl」缓存；供应商配置变更时失效。
- 设置里提供「图片输入」开关：自动检测 / 不发送。不提供「始终发送」override。
- 同一请求内按 imageId 去重；跨请求不做 base64 内存缓存。

### 3.5 图片压缩

- 上传前在 renderer 统一压缩为 WebP：
  - 最长边 2400px（小图不放大）；
  - WebP 质量 0.9；
  - 保留透明通道；
  - 动态 WebP 取首帧转静态 WebP；
  - EXIF 方向应用到像素，元数据丢弃。
- 不设固定 MB 上限，也不因压缩后体积拒绝；压缩失败才报 `IMAGE_INVALID`。
- 入库 MIME 固定 `image/webp`，文件名 `<id>.webp`。
- 这样探测请求与实际请求格式一致：探测用 WebP，入库也是 WebP，避免「探测支持 PNG、实际发 WebP 又失败」。

## 4. 内容模型

### 4.1 NoteDoc

新增 `src/shared/note-doc.ts`：

```ts

  type: 'doc';
  content: NoteParagraph[];
}

export interface NoteParagraph {
  type: 'paragraph';
  content?: NoteInline[];
}

export type NoteInline =
  | { type: 'text'; text: string }
  | { type: 'hardBreak' }
  | {
      type: 'noteImage';
      attrs: {
        imageId: string;
        alt?: string;
      };
    };

export interface StoredNoteDoc {
  version: 1;
  doc: NoteDoc;
}
```

- 运行时上传中的节点会临时多出 `uploadId` / `previewUrl`，不写入数据库；保存草稿前剔除没有 `imageId` 的节点。
- `alt` 默认「图片」；本期不做 alt 编辑。
- 文档只允许这三种 inline 和一种 block；校验失败返回 `INVALID_NOTE_DOC`。

### 4.2 纯文本投影

```ts
export const derivePlainText = (doc: NoteDoc): string => {
  const paragraphs = doc.content.map((paragraph) => {
    if (!paragraph.content) {
      return '';
    }

    return paragraph.content
      .map((inline) => {
        if (inline.type === 'text') {
          return inline.text;
        }

        if (inline.type === 'hardBreak') {
          return '\n';
        }

        // 图片不进入正文文本；用空格避免前后文字粘连
        return ' ';
      })
      .join('');
  });

  return paragraphs.join('\n').trim();
};
```

- 段落之间用 `\n`；`hardBreak` 也是 `\n`。
- 图片位置用空格占位，前后文字不会粘成一个词。
- 纯图片文档 → `''`，但保存时会被拒绝（正文必须有文字）。
- `body` 是派生结果，主进程保存时重新计算，不信任 renderer 传的文本。

其他工具函数：

```ts
export const countNoteImages = (doc?: NoteDoc | null): number;

export const docFromPlainText = (body: string): NoteDoc;
export const appendTextToDoc = (doc: NoteDoc, text: string): NoteDoc;
export const parseNoteDoc = (value: unknown):
  | { ok: true; doc: NoteDoc }

```

### 4.3 旧页面与旧草稿

- **旧页面**：`body_doc IS NULL`。`PageSnapshot.doc` 不返回；卡片按两行纯文本摘要显示；首次编辑时 `docFromPlainText(page.body)`。
- **旧草稿**：`{ body, source }` → `{ version: 2, doc: docFromPlainText(body), source }`。
- **旧备份**：没有导入功能；v1 JSON 只是旧文件，新备份为目录结构。
- **补一句**：
  - 有 `body_doc`：新文字作为新段落追加，派生 `body`，图片保留。
  - 没有 `body_doc`：沿用现有 `body + "\n\n" + content`，不创建文档。
- **编辑**：新编辑器总是发送文档；旧页面第一次保存后就有 `body_doc`。

### 4.4 正文非空约束

- 保存/编辑时 `derivePlainText(doc).trim()` 必须非空，否则 `INVALID_BODY`。
- 图片不能单独成篇；用户至少写一句。
- 旧页面本来就有非空 `body`。
- 这避免了「纯图片」对标题、引导、开场问题、FTS 的一整套特殊处理。

### 4.5 文档与正文的一致性

所有会改正文的路径都必须同时处理 `body_doc`：

| 操作      | 处理                                                                   |
| --------- | ---------------------------------------------------------------------- |
| 新建      | 有文档：`body = derivePlainText(doc)`（必须非空）；无文档：沿用 `body` |
| 编辑      | 有文档：写 `body_doc` + 派生 `body`；无文档：只写 `body`（旧客户端）   |
| 补一句    | 有文档：追加段落 + 派生；无文档：旧逻辑                                |
| 标题更新  | 不动正文/文档                                                          |
| 合上/重开 | 不动正文/文档                                                          |
| 清空全部  | 删除页面、引用、图片文件和元数据                                       |

主进程负责派生 `body`；renderer 传的 `body` 在有 `doc` 时忽略。这样避免两边算法不一致导致 FTS 和 Prompt 看到旧文本。

## 5. 图片存储

### 5.1 数据库

新增两张表（幂等建表）：

```sql
CREATE TABLE IF NOT EXISTS page_images (
  id          TEXT PRIMARY KEY,
  file_name   TEXT NOT NULL,
  mime        TEXT NOT NULL,
  byte_length INTEGER NOT NULL,
  created_at  INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_page_images_created
ON page_images(created_at);

CREATE TABLE IF NOT EXISTS page_image_refs (
  page_id  INTEGER NOT NULL REFERENCES pages(id) ON DELETE CASCADE,
  image_id TEXT NOT NULL REFERENCES page_images(id) ON DELETE CASCADE,
  PRIMARY KEY (page_id, image_id)
);

CREATE INDEX IF NOT EXISTS idx_page_image_refs_image
ON page_image_refs(image_id);
```

并给 `pages` 增加（先 `PRAGMA table_info('pages')` 检查，缺列才执行）：

```sql
ALTER TABLE pages ADD COLUMN body_doc TEXT;
```

- `page_images` 不直接挂 `page_id`，通过引用表多对多关联。
- 同一张图片可以被多条念头引用（应用内复制图片到另一条念头、复制念头等）。
- 图片内容不可变：同一个 `id` 对应的文件永远不覆盖。
- 删页面只删引用；图片行/文件由清理任务回收。
- `ON DELETE CASCADE` 依赖已有的 `PRAGMA foreign_keys = ON`。

```text

    .tmp-<uuid>          # 写入中的临时文件
  tap-along.db
```

- `file_name` 由服务端生成：`<uuid>.webp`；入库统一 WebP，不信任 renderer 文件名。
- 写入流程：
  1. 写 `images/.tmp-<uuid>`；
  2. `rename` 到 `images/<id>.<ext>`；
  3. 插入 `page_images`；
  4. 任一步失败：删除临时/目标文件，返回 `IMAGE_SAVE_FAILED`。
- 读取：协议 handler 按 id 查行、取 `file_name`、流式读文件。
- 路径校验：`path.resolve(imagesDir, file_name)` 必须仍在 `imagesDir` 下；文件名只允许 UUID + 已知扩展名。

### 5.3 输入格式与入库格式

允许输入：

| 输入 MIME    | 检测                      |
| ------------ | ------------------------- |
| `image/png`  | `89 50 4E 47 0D 0A 1A 0A` |
| `image/jpeg` | `FF D8 FF`                |
| `image/webp` | `RIFF....WEBP`            |
| `image/bmp`  | `BM`                      |
| `image/avif` | `ftyp` + `avif` / `avis`  |

- 输入格式只决定「能不能解码」；解码后统一压缩成 WebP。
- 入库 MIME 固定 `image/webp`；`page_images.mime` 只存这一个值。
- 拒绝 SVG（脚本/外链风险）、TIFF、HEIC 等浏览器不能稳定解码的格式，以及本轮不支持的 GIF。
- 空文件、无法识别、解码失败、WebP 编码失败 → `IMAGE_INVALID`。
- 发送给模型时使用 `image/webp`；能力探测也使用 WebP，格式一致。

**「输入格式白名单」是什么**

- 它指用户粘贴图片时，应用愿意接受并尝试解码的**源文件格式列表**；不是对图片内容、张数或大小的限制。
- 当前接受：
  - PNG（截图、透明图，最常见）
  - JPEG / JPG（照片）
  - WebP（网页图片；动态 WebP 取首帧）
  - BMP（部分 Windows 截图/旧图）
  - AVIF（较新的网页图片）
- 当前拒绝：
  - SVG（可能含脚本/外链，安全风险）
  - TIFF（浏览器不能稳定显示）
  - HEIC / HEIF（iPhone 常见，但 Chromium 不能直接解码，需要系统转码）
  - GIF（本轮明确不做；动图转静态涉及额外取舍）
  - 其它未知格式
- 判定看文件的 magic bytes，不看扩展名；扩展名改成 `.png` 也不会绕过。
- 接受后统一解码、压缩成 WebP；所以**最终入库文件总是 `.webp`，与输入格式无关**。
- 被拒绝时只提示「这张图片的格式不支持」，正文和已有图片不受影响。
- 如果以后需要支持 HEIC/TIFF，需要额外引入系统/库转码，另算工期。

### 5.4 不限数量，压缩但不设固定体积上限

- 不设 `MAX_IMAGES_PER_PAGE`、不设 `MAX_IMAGE_BYTES`。
- 一次可粘贴多张；文档可引用任意多张。
- 上传前统一压缩（见 §5.7），压缩后仍不因体积拒绝。
- 唯一限制来自：
  - 剪贴板/浏览器内存；
  - IPC 结构化克隆的内存峰值；
  - 磁盘剩余空间；
  - 模型供应商的请求体积、超时和计费。
- 上传并发限制为 3（技术节流，不是产品上限）。
- 超大图导致内存不足时，错误提示「这张图片没能放上，请重试或换一张」，不静默丢正文。

### 5.5 引用与共享

- 文档中的 `noteImage.attrs.imageId` 是唯一引用来源。
- 保存/编辑时，主进程从文档提取 id、去重，替换该页的 `page_image_refs`。
- 同一张图可以被多条念头引用；删除一条念头的引用不影响另一条。
- 图片行/文件只有在**没有任何引用**且超过清理期后才删除。
- 应用内复制图片到另一条念头：节点带 `data-image-id`，粘贴后引用同一个 id，保存时给新页加引用；不复制文件。

### 5.6 清理

| 对象                                   | 规则                                                     |
| -------------------------------------- | -------------------------------------------------------- |
| 没有任何引用的 `page_images` 行 + 文件 | `created_at` 超过 30 天 → 删除                           |
| 磁盘上存在、DB 没有记录的孤儿文件      | 修改时间超过 7 天 → 删除                                 |
| `.tmp-*` 临时文件                      | 超过 1 天 → 删除                                         |
| 保存/编辑时被移除的引用                | 事务提交后立即检查；无其他引用则马上删文件               |
| 清空全部数据                           | 删除所有页面、引用、图片行，并清空 `images/`             |
| 有引用但文件丢失                       | 保留 DB 行并记日志；编辑器显示破图占位；备份时记 warning |

- 启动后异步执行一次清理，不阻塞窗口。
- 清理失败只打日志，不影响使用。
- 草稿图片没有引用；如果草稿放了 30 天以上，图片可能被清掉，正文还在。这是「要清理」与「永不丢图」的折中。

**清理规则通俗说明**

- **已经保存进念头的图片永远不会被自动清理**，除非删除该念头或清空全部数据。
- **无引用图片 30 天**：指粘贴后没有保存进任何念头的图片。常见于取消编辑、保存失败、开始新念头时丢弃的草稿图。它们在数据库里没有页面引用，30 天后回收。
- **孤儿文件 7 天**：指磁盘上有文件、数据库里没有记录的文件。通常来自应用崩溃或写盘中断；它们从未被任何念头引用，7 天后回收。
- **临时文件 1 天**：指写到一半的 `.tmp-*` 文件；保存完成会重命名，没完成的就是垃圾，1 天后回收。
- 目的只是防止「取消/失败/崩溃」留下垃圾，不影响任何已保存的念头。
- 唯一可能受影响的是「放了超过 30 天的草稿」：草稿图片在保存前没有引用，可能被清掉，但草稿文字还在。如果希望更保守，可以把无引用图片保留期改成 90 天，或对草稿图片不自动清理。

### 5.7 压缩规则

| 项         | 值                            |
| ---------- | ----------------------------- |
| 输出格式   | WebP（`image/webp`）          |
| 最长边     | 2400px（小图不放大）          |
| 质量       | 0.9                           |
| 透明通道   | 保留                          |
| EXIF       | 按方向应用到像素，元数据丢弃  |
| 动态 WebP  | 取首帧转静态 WebP，不保留动画 |
| BMP / AVIF | 解码后转 WebP                 |
| 失败       | `IMAGE_INVALID`，不落库       |

- 压缩在 renderer 完成：`createImageBitmap` → canvas → `canvas.toBlob('image/webp', 0.9)`。
- 压缩后的字节仍可能很大（2400px、复杂图像），但不设固定 MB 上限。
- 入库后不可变；同一 id 的文件不覆盖。
- 这样模型请求、协议读取、备份文件都是同一种格式，能力探测与真实请求一致。

### 6.2 粘贴流程

```text
用户 Cmd/Ctrl+V
  → NoteEditor 的 handlePaste
  → 剪贴板里有 image/* 文件？
      有：
        preventDefault
        对每个文件：
          生成 uploadId，登记 File
          在光标处插入 noteImage 节点（imageId=null, uploadId）
          节点视图显示本地预览 + 转圈
          压缩成 WebP（最长边 2400、质量 0.9、动图首帧）
          异步写文件 + 建 page_images 行
          成功后把节点 attrs 改成 imageId
          失败后移除节点 + 显示错误
      没有：
        剪贴板 HTML 是否带 data-image-id（应用内复制）？
          是：交给 TipTap 默认粘贴（文字 + 图片节点）
          否：preventDefault，只插入 text/plain（保留换行），
              不把网页样式/外链图片带进来
```

细节：

- 粘贴事件里**立即启动上传**（`enqueueImage` 建任务），节点视图只是订阅同一个 Promise；即使节点视图还没挂载，上传也不会丢、pending 不会泄漏。
- 同一 `uploadId` 的上传是幂等的（节点重挂载、撤销/重做不会重复上传）。
- 上传完成前，文档里该节点没有 `imageId`；保存按钮置灰，`submit` 会等待所有上传结束。
- 保存前先 `await waitForUploads()`，再 `await nextTick()`：确保节点 attrs 更新已经通过 `onUpdate` 写回 store，避免「上传成功但保存时文档里还是 pending 节点」的竞态。
- 压缩和上传失败：移除该节点，编辑器顶部/底部显示一次错误；正文不受影响。
- 压缩在 `preparePageImage(file)` 里做；上传管理器拿到的已经是 WebP 字节。
- 用户在上传中删除节点：上传继续，完成后发现没有节点引用它，调用 `removePageImage`（无引用才删文件）；否则留给清理。
- 一次粘贴多张：按剪贴板顺序插入；并发上传最多 3 个。
- 粘贴文本：保留换行；不解析 Markdown；不保留 HTML 格式。
- 粘贴应用内图片：靠 `data-image-id` 识别，共享同一图片 id。

## 7. 保存、编辑、补一句

### 7.1 新建

```text
NoteEditor.getJSON()
  → 等待所有 pending 上传
  → 去掉没有 imageId 的节点
  → body = derivePlainText(doc)
  → 如果 body 为空：报「先写下一个念头」
  → savePage({ doc, source, parentPageId })
  → 主进程：
       parseNoteDoc(doc)
       body = derivePlainText(doc)（必须非空）
       imageIds = collectNoteImageIds(doc)
       事务：INSERT pages (body, body_doc)
             INSERT page_image_refs
             INSERT pages_fts
             写 opening 消息 / 父页 fork 锚点
  → 返回 PageSnapshot（body + doc）
  → 卡片两行摘要 + 含图标记
```

- 正文为空（即使有图）：`INVALID_BODY`，前端显示现有「先写下一个念头」。
- 图片 id 不存在：`IMAGE_NOT_FOUND`，整个事务回滚，正文不落库。
- 父页 fork 锚点、标题生成、理解引导逻辑不变。

### 7.2 编辑

```text
startEditing
  → editDoc = page.doc ?? docFromPlainText(page.body)
  → 编辑器挂载
保存
  → 等待上传
  → body = derivePlainText(editDoc)（必须非空）
  → editPage({ pageId, doc, requestId })
  → 主进程：
       校验文档/图片/正文非空
       body = derivePlainText(doc)
       事务：UPDATE pages SET body=?, body_doc=?, ...
             replace refs
             计算失去引用的图片文件
       提交
       删除失去引用的文件（无其他引用）
  → 返回 PageSnapshot
  → store 用响应回写 page.body/title/doc
取消
  → editDoc 丢弃
  → 本次新上传、且不在 page.doc 里的图片 best-effort 删除
```

- 编辑已有图片：从文档里删掉节点只是不再引用；保存时才替换引用。
- 编辑取消：原图片引用没动，图片仍可用；新粘的图片无引用，尽量即时删除，删不掉交给清理。
- 保存失败：保留编辑态和文档，不清空。
- 保存成功后，best-effort 删除「本次会话上传、但最终文档里已不存在」的图片（无引用才删）。
- 只改图片、不改文字：`body` 不变；标题/引导不会因图片变化而刷新。

### 7.3 补一句

- `appendText` 读取页面：
  - 有 `body_doc`：`appendTextToDoc` 追加段落，派生 `body`，更新 `body_doc`，引用不变。
  - 没有 `body_doc`：沿用原逻辑，只改 `body`。
- 补一句成功后，store 用响应里的 `doc`/`body` 回写，不再自己拼字符串。
- 补一句仍不支持图片输入（它是对谈输入框，不是正文编辑器）。

### 7.4 删除图片

- 删除节点 → 文档变化 → 保存时引用被替换 → 无其他引用的文件删除。
- 不立即删文件，避免「删除后撤销」拿到破图。
- 草稿里删除图片：无引用，30 天清理；用户清空草稿/开始新念头时可 best-effort 立即删。
- 应用内复制图片到另一条念头：引用共享，删除其中一条不影响另一条。

## 8. IPC 与数据契约

### 8.1 页面 payload

```ts
export interface SavePagePayload {
  doc?: NoteDoc; // 新客户端必传
  body?: string; // 旧客户端/测试兼容；有 doc 时忽略
  source: string;
  parentPageId?: number;
}

export interface EditPagePayload {
  pageId: number;
  doc?: NoteDoc; // 新客户端必传；旧客户端用 body
  body?: string;
  requestId: string;
}
```

- `doc` 优先；有 `doc` 时主进程派生 `body`，并校验/提取图片。
- 没有 `doc` 时保持旧行为（纯文本、无图片）。
- 旧页面有图片但客户端不传 `doc` 的编辑请求：拒绝（`INVALID_NOTE_DOC`），避免抹掉图片。
- 正文非空约束在两条路径都执行。

### 8.2 图片通道

```ts
export const IMAGE_CHANNELS = {
  create: 'images:create',
  remove: 'images:remove',
} as const;

/** 入库统一 WebP；输入格式在 renderer 解码后压成 WebP。 */
export type PageImageMime = 'image/webp';

export interface PageImageMeta {
  id: string;
  mime: PageImageMime;
  byteLength: number;
}

export interface CreatePageImagePayload {
  bytes: Uint8Array; // 已压缩的 WebP 字节
  mime: 'image/webp';
}

export interface CreatePageImageResult {
  ok: boolean;
  image?: PageImageMeta;
  errorCode?: AppErrorCode;
}

export interface RemovePageImageResult {
  ok: boolean;
  errorCode?: AppErrorCode;
}
```

- 没有 `images:get`：读取走 `tap-image://`。
- 没有 `imageIds` 参数：文档本身就是引用来源。
- `remove` 只删「没有任何页面引用」的图片；被引用的返回成功但不删（幂等）。
- 主进程生成 id（UUID），不接受 renderer 指定 id。
- 主进程只接受 WebP magic；其它格式说明 renderer 没压缩，直接拒绝（`IMAGE_INVALID`）。

### 8.3 快照与记录

### 9.5 `tap-image://` 协议

新增 `src/main/services/tap-image-protocol.ts`：

- `registerTapImageScheme()`：在 `app.ready` 前调用 `protocol.registerSchemesAsPrivileged`。
- `registerTapImageHandler({ protocol, images, imageStore })`：

```ts
protocol.handle('tap-image', async (request) => {
  const url = new URL(request.url);

  if (url.host !== 'img') {
    return new Response('Not found', { status: 404 });
  }

  const imageId = decodeURIComponent(url.pathname.replace(/^\//, ''));

  if (!isUuid(imageId)) {
    return new Response('Not found', { status: 404 });
  }

  const row = images.find(imageId);

  if (!row) {
    return new Response('Not found', { status: 404 });
  }

  const stats = await imageStore.stat(row.file_name);

  if (!stats) {
    return new Response('Not found', { status: 404 });
  }

  const stream = Readable.toWeb(imageStore.createReadStream(row.file_name));

  return new Response(stream as ReadableStream, {
    headers: {
      'Content-Type': row.mime,
      'Content-Length': String(stats.size),
      'Cache-Control': 'private, max-age=31536000, immutable',
      'X-Content-Type-Options': 'nosniff',
    },
  });
});
```

- 在 `main.ts` 顶部（`app.ready` 前）注册 scheme；初始化数据库后注册 handler；再创建窗口。
- 开发/生产都走同一个协议；renderer 不需要知道文件路径。
- 若以后加 CSP，需要允许 `img-src 'self' tap-image: blob: data:`（当前没有 CSP meta）。

#### 9.9.4 `ImageContextService`

新增 `src/main/services/image-context.ts`：

```ts
export interface ChatImageData {
  mime: string;
  dataUrl: string;
}

export interface ImageContextResolver {
  resolve(imageId: string): Promise<ChatImageData | null>;
}

export class ImageContextService implements ImageContextResolver {
  constructor(
    private readonly images: Pick<PageImagesRepository, 'find'>,
    private readonly store: Pick<ImageStore, 'read'>,
  ) {}

  async resolve(imageId: string): Promise<ChatImageData | null> {
    const row = this.images.find(imageId);

    if (!row) {
      return null;
    }

    const bytes = await this.store.read(row.file_name);

    if (!bytes) {
      return null;
    }

    return {
      mime: row.mime,
      dataUrl: `data:${row.mime};base64,${Buffer.from(bytes).toString('base64')}`,
    };
  }
}
```

- 不设大小/数量上限。
- 文件缺失返回 `null`；gateway 用文本占位 `[image unavailable]`，不阻断整次请求。
- 同一请求内按 imageId 去重，避免重复 base64。
- 不做跨请求缓存，避免大图长期占内存；如果后续需要，可加 LRU。

发送前：

```ts
const buildProviderMessages = async (
  messages: ChatMessage[],
  resolver?: ImageContextResolver,
): Promise<ProviderMessage[]> => {
  const cache = new Map<string, Promise<ChatImageData | null>>();

  const resolve = (imageId: string) => {
    if (!resolver) {
      return Promise.resolve(null);
    }

    let pending = cache.get(imageId);

    if (!pending) {
      pending = resolver.resolve(imageId);
      cache.set(imageId, pending);
    }

    return pending;
  };

  return Promise.all(
    messages.map(async (message) => {
      if (!message.imageIds?.length || message.role !== 'user') {
        return { role: message.role, content: message.content };
      }

      const parts: ProviderContentPart[] = [
        { type: 'text', text: message.content },
      ];

      for (const imageId of new Set(message.imageIds)) {
        const image = await resolve(imageId);

        parts.push(
          image
            ? {
                type: 'image_url',
                image_url: { url: image.dataUrl },
              }
            : { type: 'text', text: '[image unavailable]' },
        );
      }

      return { role: message.role, content: parts };
    }),
  );
};
```

- `complete` / `stream` 在构造 provider messages 之前先判断能力：

```ts
const hasImages = messages.some((message) => message.imageIds?.length);
const supportsImages = hasImages
  ? ((await capabilities?.supportsActive()) ?? true)
  : true;
const effectiveMessages = supportsImages
  ? messages
  : messages
      .filter((message) => !message.imageContext)
      .map(
        ({ imageIds: _imageIds, imageContext: _imageContext, ...message }) =>
          message,
```

- `true`：按上面的逻辑解析 data URL 并发送图片；

- `imageIds` 字段不会出现在请求体里。
- 只有 user 消息带图；system/assistant 即使误带也忽略。
- `imageContext: true` 的消息在能力不支持时整条丢弃，避免「说有图但没图」。

| --------------------- | ------------------------------------------------- |
| 2xx                   | `supported`                                       |
| 400 / 415 / 422       | `unsupported`                                     |
| 401 / 403 / 404       | `unsupported`（本次纯文本；主请求仍有自己的错误） |
| 429 / 网络错误 / 超时 | `unknown`（本次纯文本，稍后重试）                 |

- 探测请求不写开发者请求记录，不计入老师对话。
- 探测只发一张 WebP；与实际入库格式一致。

**缓存**

- 存在 electron-store 的 `imageCapabilities`；key 为 `providerId`，值为 `{ model, baseUrl, status, checkedAt }`。
- `supported` / `unsupported` 缓存 7 天；`unknown` 缓存 10 分钟。
- provider 保存、切换 key、model/baseUrl 变化时清掉对应缓存。
- 并发请求共用同一个 in-flight probe promise，避免同时打多次。

**决策**

```ts
resolve(id): Promise<ImageCapabilityDecision>
```

1. `imageInput === 'off'` → unsupported（override）；
2. 缓存命中且未过期 → cache；
3. 否则探测 → probe / unknown；
4. 探测 `unknown` 时，本次按 `unsupported` 处理（纯文本），但缓存短 TTL，稍后重试。

**Gateway 使用**

- 只在消息里真的带 `imageIds` 时才调用 `supportsActive()`；纯文字请求不探测。
- `false` → 去掉所有 `imageIds`，消息回到纯文本；老师的回答流程继续。
- `true` → 发多模态 parts。
- 能力检测不会让请求失败；最坏情况是这次不带图。

**设置页与提示**

- provider 设置增加「图片输入」：自动检测 / 不发送。
- 显示缓存状态：支持 / 不支持 / 未检测 / 检测中。
- 提供「重新检测」按钮（`providers:probe-images`）。
- renderer 在已知 `unsupported` 且念头含图时显示一句：「当前模型不支持图片输入，图片不会发送给模型；可在设置里手动开启。」
- `unknown` 时不提示，首次带图请求会探测。
- 没有「始终发送」override：探测为不支持时一律不发送，避免供应商拒绝打断流程。

**隐私**

- 探测只发送内置极小图，不发送用户图片。
- 只有判定 supported 后，用户图片才会离开本机。

### 10.4 `image-uploads.ts`

```ts
export const pendingUploads = ref(0);
export const imageUploadError = ref<AppErrorCode | null>(null);

export const enqueueImage = (file: File): {
  uploadId: string;
  previewUrl: string;
};

export const startUpload = (uploadId: string): Promise<PageImageMeta>;
export const waitForUploads = (): Promise<void>;
```

- `enqueueImage`：生成 uploadId，存 File，建 `URL.createObjectURL(file)`，`pendingUploads += 1`，并**立即调用 `startUpload`**。
- `startUpload`：按 uploadId 幂等；先 `preparePageImage(file)` 压成 WebP，再 `pageImageApi.create({ bytes, mime: 'image/webp' })`；成功后返回 meta；失败抛错并设置 `imageUploadError`；`finally` 减少 pending。
- `waitForUploads`：等待当前所有任务结束（用于保存兜底）；调用方随后 `await nextTick()`。
- 并发上限 3：简单队列或 Promise 池。
- 不因大小/数量拒绝；压缩失败才报 `IMAGE_INVALID`。
- 失败后节点被移除，pending 归零，保存可以继续。

#### 10.4.1 `image-prepare.ts`

```ts
export const preparePageImage = async (
  file: File,
): Promise<
  | { ok: true; bytes: Uint8Array; mime: 'image/webp' }
  | { ok: false; errorCode: 'IMAGE_INVALID' }
>;
```

- 用 `createImageBitmap(file)` 解码；失败 → `IMAGE_INVALID`。
- 计算等比缩放：最长边超过 2400 才缩小；小图不放大。
- 画到 canvas；透明通道保留；`canvas.toBlob('image/webp', 0.9)`。
- 动态 WebP 只取首帧；BMP/AVIF 同样解码后转 WebP；GIF 在输入阶段直接拒绝。
- 输出字节为空或编码失败 → `IMAGE_INVALID`。
- 不设固定 MB 上限；解码超大图的内存/时间受设备限制。
- 原始 EXIF 方向由 `createImageBitmap` 应用；输出不带元数据。

## 11. 图片作为模型上下文

### 11.1 标题与摘要

- 标题仍基于 `body` 文本；图片不参与标题生成。
- 卡片仍两行文本摘要；图片数量只作为标记。
- 纯图片念头不允许，因此不存在「无文字标题」问题。

### 11.2 FTS / 检索

- `body` 不含图片；FTS 不变。
- 含文字+图片的念头按文字检索。
- 图片不参与关键词提取、相关念头、上下文压缩。

### 11.3 理解引导

- 若当前供应商图片能力为 `supported`：带当前页图片；否则本次纯文本请求继续。
- 有文字：照常生成。
- 当前念头的图片随引导请求发送（`imageIds` 挂在 user 消息上）。
- 相关旧念头只发文字；不把历史图片塞进引导请求。
- 引导的 `bodyHash` 仍基于 `body`；只改图片不会刷新引导（AI 虽然能看到图，但本轮不因图片变化重新规划；这是为了避免每次插图都触发一次模型调用）。

### 11.4 老师对谈

- 仅当能力检测为 `supported` 时带图；否则本次纯文本，老师回答流程不中断。
- 老师提问：当前页文字 + 当前页图片。
- 恢复上下文：目标页文字/图片 + 被连接页文字/图片；压缩上下文/相关念头只发文字。
- 维护（编辑/补一句后）：当前页文字 + 当前页图片。
- 图片以额外的 user 消息发送，文本明确「这些图片属于当前念头，是上下文，不是新的请求」。
- 会话历史中的旧消息不重复附图；每轮只带当前页（或恢复时的两页）图片。

### 11.5 联网问答与意图路由

- 仅当能力检测为 `supported` 时带图；否则纯文本继续。
- 意图路由：当前页文字 + 图片，用于判断问题是否指向图片内容。
- 联网问答：当前页文字 + 图片 + 网页证据文字；网页来源不发图片。
- 研究结果的引用仍只针对网页来源；图片不参与 `[n]` 引用。

### 11.6 请求格式

- 文本 + 图片：
  ```json
  {
    "role": "user",
    "content": [
      { "type": "text", "text": "..." },
      {
        "type": "image_url",
        "image_url": { "url": "data:image/webp;base64,..." }
      }
    ]
  }
  ```
- 纯文本：保持原来的字符串 content，完全兼容现有供应商。
- `imageIds` 不进入请求体。
- 同一请求内去重；不同请求不共享 base64 缓存。

### 11.7 供应商兼容性与能力检测

- 只支持 OpenAI 兼容的 `image_url` part；不支持 Anthropic/Gemini 原生格式。
- 发送前通过 `ImageCapabilityService` 判断当前供应商/model 是否支持图片：
  - 支持：发送图片 parts；
  - 不支持：去掉 `imageIds`，纯文本请求继续；
  - 未检测/探测失败：本次按纯文本处理，短时间后重试探测。
- 入库统一 WebP，因此不需要再考虑 BMP/AVIF 的供应商格式差异。
- 大图/多图可能触发供应商的请求体积限制或超时；不设应用侧上限。
- 没有「始终发送」override：检测为不支持时一律不发送。

### 11.8 请求记录与隐私

- 开发者请求记录只存脱敏后的文本 + `[images: N]` 标记，不存 base64。
- 能力检测判定 `supported` 后，图片会发送给当前配置的模型供应商；供应商的数据留存策略不在应用控制范围内。探测本身只发送内置 64×64 WebP。
- 设置页常驻提示：「含图片的念头会在能力检测支持时，把图片发送给当前模型供应商。」
- 编辑器首次粘贴图片时显示一次性提示，用户确认后写入 localStorage `tap-along:image-privacy-notice`，不再重复。
- 如果 README、首用页或设置页已有「数据只在本机」类表述，需要同步补一句「图片会随模型请求发送给当前供应商」，避免隐私承诺不一致。

## 12. 兼容性、迁移与回滚

### 12.2 旧草稿

- `{ body, source }` 自动转成 `{ version: 2, doc, source }`。

### 12.4 回滚

- 新版本同时维护 `body`；退回旧版本后，文字内容仍可读。
- 旧版本看不到图片（`body` 不含图片），图片文件和 `body_doc` 保留。

- 数据库迁移只加列/表，不回滚数据。

## 13. 安全、隐私与性能

### 13.1 安全

1. 主进程按 magic bytes 判定格式，不信任 `file.type`/扩展名。
2. 拒绝 SVG；图片通过 `<img>` 渲染，不使用 `innerHTML`。
3. 协议只接受 `img/<uuid>`，按 DB 行取文件名，做目录边界校验。
4. `body_doc` 严格 schema 校验；未知节点/非法类型拒绝。
5. 粘贴 HTML 时不保留样式/链接/外链图片；只插入纯文本或应用内图片节点。
6. 导出只复制已知文件；不跟随用户输入路径。
7. 只有能力检测判定 supported 后，用户图片才会发送给模型供应商；探测只发内置极小 WebP。开发者记录脱敏。

### 13.2 性能

| 点       | 处理                                                                   |
| -------- | ---------------------------------------------------------------------- |
| 图片读取 | 协议流式读文件；长缓存；编辑器/浮层内 `loading="lazy"`；读态卡片不加载 |
| 图片压缩 | 上传前 WebP 最长边 2400、质量 0.9；减少磁盘和模型请求体积              |
| 能力检测 | 每个 provider/model 只探测一次并缓存 7 天；并发共用 in-flight          |
| 数据库   | 只存元数据；body_doc 只有文字 + id                                     |
| 列表     | 不读图片字节；不 JOIN（doc 已含 id）                                   |
| 编辑器   | 只加载当前念头图片；多图时滚动                                         |
| 草稿     | 只存 doc 文本 + id，不存字节                                           |
| 备份     | 逐文件 `copyFile`，不整体进内存                                        |
| 清理     | 启动后异步；不阻塞窗口                                                 |
| 模型请求 | 每轮重新 base64；不跨请求缓存；大图/多图可能慢                         |

### 13.3 已知边界

- 一条念头放几百张大图时，编辑器会同时渲染大量 `<img>`；浏览器解码压力大。用户要求不限数量，这是必然代价。
- 单张超大图（接近内存上限）会在粘贴/解码/base64 时卡顿或失败；没有固定 MB 上限。
- 模型请求带大量图片时，供应商可能返回体积/计费/超时错误。
- 读态卡片不展示图片；完整图文通过「查看全文」浮层查看，浮层按需加载。
- 能力探测可能误判：支持图片的供应商可能拒绝探测用的极小 WebP；此时图片不会发送，可在设置里重新检测。
- 压缩有损（WebP 0.9，最长边 2400）；动图只保留首帧；需要原始像素时无法恢复。

## 17. 风险与应对

| 风险                                        | 影响                       | 应对                                                        |
| ------------------------------------------- | -------------------------- | ----------------------------------------------------------- |
| TipTap/ProseMirror 与 Vue/Electron 集成问题 | 编辑器不可用               | 先做 P0 垂直切片；锁定版本；E2E 覆盖粘贴/IME                |
| contenteditable 中文 IME 回归               | 输入体验变差               | 不在 composition 期间重设 DOM；用成熟编辑器；手工重点验收   |
| 文档与 `body` 派生不一致                    | FTS/Prompt 看到旧文本      | 主进程统一派生；所有写路径单测；保存时不信任 renderer body  |
| 能力探测误判                                | 支持图片的供应商被跳过     | 设置里重新检测；探测 7 天缓存；不提供强制发送               |
| 供应商支持图片但不支持 WebP                 | 探测判为不支持，图片被跳过 | 探测与入库都统一 WebP；需要兼容更多格式时再做 JPEG/PNG 转码 |
| 供应商不支持图片                            | 请求中断                   | 检测到后去掉图片，纯文本继续；设置页显示状态                |
| 图片请求体积/费用/超时                      | 请求失败或很慢             | 压缩到 2400px/WebP；不设应用上限；单请求去重                |
| base64 内存峰值                             | renderer/主进程卡顿        | 压缩后再 base64；按请求解析、不跨请求缓存                   |
| 隐私：图片发往供应商                        | 用户预期变化               | 只有 supported 才发送；文档/UI 提示；请求记录脱敏           |
| 旧版本回滚后编辑含图念头                    | 文档变旧，丢新文字         | 回滚说明；回滚前导出；不在旧版本编辑含图念头                |
| 不限大小导致内存峰值                        | 粘贴/加载卡顿或失败        | 压缩但不设假上限；提示失败；并发上传限 3                    |
| 读态卡片看不到图                            | 用户需打开全文浮层         | 卡片显示含图标记 + 查看全文；浮层按需加载                   |
| 压缩有损                                    | 细节丢失                   | WebP 0.9/最长边 2400；在验收中写明                          |
| 图片文件清理误删                            | 念头破图                   | 引用表 + 30 天宽限；删除在事务提交后；启动检查引用          |
| 孤儿文件累积                                | 磁盘占用                   | 启动清理 + 临时文件清理 + 清空数据                          |
| 协议在开发/生产差异                         | 图片加载失败               | 开发/生产同一协议；E2E 验证；scheme 在 ready 前注册         |
| 备份目录 UX 变化                            | 用户不习惯                 | 明确文案；目录结构简单                                      |
| 现有测试大量断言                            | 改造回归多                 | `doc` 可选、旧路径不传 doc；分阶段跑测试                    |
| happy-dom 不支持 ProseMirror                | 单测覆盖不足               | 纯逻辑抽 shared；编辑器用 E2E/手工                          |
| SVG/恶意图片                                | 安全风险                   | 格式白名单 + magic + 不执行脚本 + 协议限 id                 |

## 18. 确认结论

- **输入格式**：PNG / JPEG / WebP / BMP / AVIF；拒绝 SVG、TIFF、HEIC、GIF。GIF 本轮不做。
- **清理保留期**：维持 30 / 7 / 1。
- **已保存进念头的图片：永远不会自动删除。**
- 无引用图片 30 天：粘贴后没保存进任何念头的图片（取消编辑、保存失败、丢弃草稿）在 30 天后回收。
- 孤儿文件 7 天：磁盘上有文件、数据库里没记录的垃圾文件，7 天后回收。
- 临时文件 1 天：写到一半的 `.tmp-*` 文件，1 天后回收。
- 唯一副作用：放了超过 30 天的草稿，图片可能被清，文字还在。

## 19. 实施顺序

```text
D1 NoteDoc 模型 + 单测
  → D2 数据库迁移 + 图片仓储 + 引用
  → D3 文件存储 + 协议 + IPC
  → D4 TipTap 编辑器 + 图片节点 + 压缩（真机最先看到效果）
  → D5 读态含图标记 + 查看全文浮层 + 大图预览
  → D6 store/草稿/编辑/补一句 + 正文非空
  → D7 导出目录 + 清理
  → D8 多模态模型上下文 + 记录脱敏
  → D9 图片能力检测 + 自动降级 + provider 设置
  → D10 E2E + 回归 + 手工验收
```

建议先做一条**垂直切片**：

```text
启动 → 新建 → 写一句 + 粘一张图 → 压缩上传 → 保存
→ 卡片显示两行摘要 + 含图标记 + 查看全文
→ 浮层看到图文 → 重启仍在
```

这条链路打通后，再补多模态请求、能力检测、导出、清理和边界情况。这样能尽早验证 TipTap、压缩、协议、文件存储四件事是否都成立。
